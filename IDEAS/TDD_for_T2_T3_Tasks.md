# TDD для T2/T3 задач

## Статус

Идея предварительно одобрена. Реализация ещё не проектировалась в деталях.

## Суть

DevRails уже проводит задачу от принятого требования через планирование,
исполнение и независимую проверку. Однако тест, подтверждающий новое поведение,
может появиться уже после production-кода. В таком случае он хорошо фиксирует
получившуюся реализацию, но слабее доказывает, что изначально выражал именно
ожидаемый результат.

Идея состоит в том, чтобы для T2/T3 задач в стадии `execute` появилось
наблюдаемое движение `RED -> GREEN`. До реализации test или другой подходящий
probe показывает отсутствие требуемого поведения, а после реализации та же
проверяемая претензия получает положительное evidence.

RED здесь ценен не как ритуал TDD. Он создаёт момент правды между
спецификацией и кодом: проверка уже понимает желаемый outcome, а реализация ещё
не успела повлиять на её формулировку.

## Место в существующем workflow

Новый самостоятельный этап для этого не нужен. Для scheduler задача всё ещё
проходит обычную стадию `execute`, а её lifecycle остаётся прежним.

```text
accepted task outcome
  -> task-scoped test/probe
  -> RED evidence
  -> implementation
  -> GREEN evidence
  -> independent /verify
  -> existing tier-routed /red-verify
```

Во время планирования у T2/T3 задачи появляется понятная связь между принятым
claim и способом увидеть его первоначальный failure. Planning review оценивает,
насколько такой путь реалистичен. Исполнение оставляет RED/GREEN evidence в
обычных task protocol и artifact paths, а `/verify` независимо подтверждает
финальное поведение по тому же claim.

`/red-verify` сохраняет свою нынешнюю роль. RED/GREEN доказывает функциональное
изменение, но не заменяет hostile semantic review сложных последствий.

## Почему только T2/T3

Для T0/T1 обязательная RED-фаза часто создавала бы больше церемонии, чем
уверенности. Небольшая документационная или локальная правка и сейчас может
быть надёжно подтверждена компактным evidence.

У T2/T3 цена ложного успеха выше. Такие задачи чаще меняют API, данные,
состояния, миграции, security properties, несколько компонентов или
production-sensitive поведение. Здесь разница между «тест написан после кода»
и «тест заранее поймал отсутствующее поведение» уже материальна.

При этом tier сам по себе не делает RED осмысленным. Внутренний рефакторинг без
изменения поведения, уже существующий contract или чисто механический outcome
могут иметь более честный proof path. В task handoff поэтому полезно различать
случаи, где RED действительно ожидается, и случаи, где он неприменим по
конкретной причине.

## Что считается настоящим RED

Содержательный RED показывает именно отсутствие или неверность принятого
поведения. Его failure связан с task-scoped acceptance claim и воспроизводится
в подходящей среде.

Синтаксическая ошибка, сломанный import, неверный test setup, несвязанное
падение или безусловный `NotImplemented` ничего не говорят о продуктовой
претензии. Такой failure выглядит красным технически, но не создаёт доверия к
будущему GREEN.

Искусственное повреждение fixture или ослабление assertion ради демонстрации
цикла имеет ту же проблему: механизм начинает обслуживать собственную
формальность вместо результата пользователя.

Если проверка оказывается зелёной ещё до реализации, это тоже полезная правда.
Возможно, требуемое поведение уже существует, task plan устарел или задача
на самом деле относится только к coverage. Код в таком случае не нуждается в
искусственной поломке ради красивого RED.

## Особенность T3

Для T3 ценность RED сохраняется только пока он не повышает реальный риск.
Проверка опасного поведения естественно живёт в sandbox, disposable
environment, temporary database, reversible migration fixture, dry-run, mock
provider или другом изолированном контуре.

Реальный платёж, production write, необратимая миграция, удаление рабочих
данных или временное ослабление security boundary не становятся приемлемыми
только потому, что нужны для TDD.

У T3 также может быть несколько независимо опасных claims. Один probe способен
покрыть их вместе, если его наблюдения действительно относятся ко всему
значимому риску. Формальное наличие одного красного теста само по себе такой
полноты не доказывает.

## Связь со спецификацией

RED и GREEN имеют смысл только при устойчивой ссылке на то, что они
подтверждают. Для product behavior естественной опорой выглядит стабильный
feature acceptance ID. Для Foundation-задач или технических outcomes без
feature AC такой опорой может быть `REQ-000` либо точный canonical spec anchor.

Это сближает идею с более широким Acceptance Trace Contract:

```text
REQ / canonical claim
  -> task-scoped acceptance
  -> RED evidence
  -> implementation
  -> GREEN evidence
  -> verification verdict
```

Точный способ хранения этой связи остаётся частью будущей реализации.
Существующие `evidence_required`, task links и protocol evidence уже дают
подходящую поверхность, поэтому отдельная task schema или второй registry не
выглядят обязательными.

## Сохранение текущих rails

Идея не предполагает новых task statuses, scheduler stages, verdicts,
protocol families или testing queue. Ownership также остаётся узнаваемым:
`/exe` отвечает за реализацию и её handoff, `/verify` — за независимый
functional verdict, `/red-verify` — за semantic verdict, а lifecycle owner —
за итоговое состояние задачи.

RED является evidence текущего Execution Attempt, а не разрешением закрыть
задачу. GREEN, полученный исполнителем, остаётся входом для verifier, но не
подменяет независимую проверку.

Исторические `done|failed` задачи не получают выдуманный RED задним числом.
Для существующих незавершённых очередей новый подход естественно появляется
при очередном плановом reconciliation, не меняя task identity и накопленное
состояние.

## Ожидаемый результат

После появления механизма свежий исполнитель T2/T3 задачи видит не только
список будущих проверок, но и понимает, какое принятое поведение должно сначала
оказаться отсутствующим. Реализация начинается уже после того, как этот
контракт стал наблюдаемым.

Для пользователя это означает меньше «зелёных» результатов, которые лишь
подтверждают удобную для написанного кода интерпретацию. Для агента — более
короткий путь от спецификации к честному evidence без нового слоя workflow
церемонии.
