# DevRails Nav 27

Проектирование плагина навигации по AI-разработке внутри DeepSeek Harness.
Документ фиксирует решения пользователя и обновлённое архитектурное предложение.
Исполнение плагина ещё не реализовано. Расположение карты согласуется по
визуальному референсу до реализации UI.

## Принятые решения

- Название: **DevRails Nav 27**. Железнодорожная метафора сохраняется.
- UI строится на **Svelte 5**. Карта сначала схематичная, с последующим
  улучшением оформления. Графика карты — SVG; формы и чат — HTML.
- Все модели, оркестратор, исполнители, reviewers, Judge и Side Chat работают
  через штатную агентную среду DSH. Codex App Server и внешние агентные среды
  исключены. Выбор модели не меняет способ запуска агента.
- Большинство прежних требований DevRails становятся изменяемыми настройками
  по умолчанию. Это намеренное изменение контракта новой версии.
- Любого verify-участника, включая основного, можно отключить. При отсутствии
  включённых участников verify пропускается. red-verify также отключаем.
- Отключённая проверка не требует своего отчёта и не препятствует закрытию
  успешно реализованной задачи. В результате явно указано отсутствие проверки.
- Механическая часть scheduler переходит из инструкций в код. Семантические
  решения остаются моделям.
- Модель инициирует запрос на изменение маршрута, включая возврат к PRD.
  В обычном режиме запрос появляется в основном чате DSH, на карте — путь
  в туннель и красный светофор. Переход начинается после зелёного от пользователя
  либо его согласия в чате. В `/autonomous` решение модели принимается
  автоматически, без вопроса пользователю. Явную остановку пользователя
  автономный режим не отменяет.
- Такое ожидание решения применяется ко всем нестандартным ответвлениям
  и к консультациям перед продолжением основного пути. Общий короткий формат
  обратной связи модели сообщает о необходимости решения; контроллер добавляет
  конкретные инструкции и схему уточнения только по возникшей ситуации.
- Основной чат остаётся в штатном интерфейсе DSH; клик по машинисту должен
  открывать сессию оркестратора. Клик по корпусу поезда создаёт отдельный Side Chat,
  закреплённый ниже текущего положения на карте до удаления через DEL в чате.
- Смена оркестратора доступна, когда поезд остановлен. Настройки остальных
  исполнителей можно менять во время движения для следующих запусков.
- Memory Bank остаётся долговременным контекстом, позволяющим продолжить
  работу в новой сессии после обрыва.
- KISS важнее сохранения прежней строгости или полной совместимости с DevRails 26.

## Предлагаемая архитектура

DSH host-плагин с небольшим контроллером DevRails и самостоятельная веб-страница
с картой, настройками, агентами и Side Chat. Предлагается отдавать страницу
тем же сервером DSH по собственному маршруту, например `/nav27/`.
Компоновка страницы независима от стандартных панелей DSH; подключение,
вызовы и потоки событий используют штатные механизмы платформы.

```text
Nav UI ↔ DSH RPC / streams ↔ Nav controller
                              ├─ DSH orchestrator session
                              ├─ DSH native subagents
                              └─ Memory Bank / task cards / project files
```

DSH владеет модельным циклом, провайдерами, инструментами, сессиями,
permissions и compaction. Nav использует эти механизмы, а не реализует их заново.

| В коде Nav | У моделей |
| --- | --- |
| Очередь, зависимости и текущая операция | Понимание задачи, PRD и архитектура |
| Запуск включённых ролей и сбор результатов | Реализация, анализ и review |
| Настройки и их снимок для запуска | Содержательная оценка findings |
| Обычный переход, skip, повтор, Pause/Stop | Выбор маршрута исправления при неоднозначности |
| Запись lifecycle и фактически пройденных проверок | Решение, каких сведений не хватает для работы |
| Формирование краткого контекста операции из доступных источников | Оценка достаточности имеющегося контекста |

Для стандартного перехода отдельный запрос к оркестратору не нужен.
Если результат требует содержательного выбора, оркестратор сообщает об этом
через общий feedback. Контроллер уточняет решение при необходимости, получает
разрешение согласно режиму и продолжает выбранную операцию.

Операции описываются небольшим фиксированным набором данных и обработчиков.
Универсальный конструктор графов и отдельный движок workflow не требуются.

## Общая обратная связь и уточнение по ситуации

Предлагается один небольшой формат управления flow для завершения операции
или сообщения о необходимости решения. Эскиз общей части:

```json
{
  "flow": "needs_decision",
  "message": "В требованиях противоречие; нужно обсудить изменение PRD"
}
```

`continue` означает, что модель не запрашивает дополнительное решение;
`needs_decision` — что продолжение требует разбора. Это сигнал управления,
не замена предметного результата, verdict проверки или ошибки исполнения DSH.
Он не отправляется после каждого инструмента, токена или внутреннего шага модели.

При `continue` контроллер использует результат операции и её обычный маршрут.
При `needs_decision` продвижение приостанавливается. Если сведений недостаточно,
контроллер даёт модели только относящийся к ситуации вопрос и компактную схему
ответа: например, уточнить изменение требований, предложить возврат или
сформулировать консультацию без смены следующей операции. Содержательный выбор
остаётся у модели; код не определяет маршрут по ключевым словам свободного текста.

Модель не получает одновременно все ветки DevRails, отдельный инструмент для
каждого возврата и полный набор схем исключений. В её рабочем контексте остаются
текущая цель, доступные результаты, общий feedback и необходимое сейчас уточнение.
Состав переходов и выбор контекста уточнения принадлежат описаниям операций
контроллера. Если подходящая детализация уже получена, повторный обмен не нужен.
Экономия на постоянных инструкциях может потребовать дополнительного модельного
хода в нестандартной ситуации; он не добавляется на каждый штатный переход.

После уточнения контроллер хранит один ожидающий запрос решения: причину,
вопрос, конкретное предложение и, если меняется маршрут, его цель. При консультации
на основном пути красный появляется перед обычным следующим шагом; туннель
не нужен. При возврате появляется предложенная туннельная ветка. В обоих случаях
согласие в основном чате и зелёный в Nav разрешают один и тот же запрос.
Зелёный означает согласие с показанным предложением; если требуется сообщить
неизвестные сведения, их нужно получить в чате, нажатие не создаёт эти сведения.

При дальнейшем полном разборе canonical commands, workflows и handoffs нужно
составить каталог нестандартных переходов: источник, условие, цель или консультация
на текущем пути, требуемое решение и место продолжения. Проверяются также repair,
повторные проверки и blocker/resume-ветки. Наличие ветки в старом контракте само
по себе не разрешает выполнить её без пользователя в обычном режиме.
Полный каталог ещё не составлен; прежние обязательные gates в него автоматически
не переносятся. Все такие ситуации используют общий механизм ожидания решения,
с уже принятой политикой автоматического разрешения в `/autonomous`.

## Решение модели и изменение маршрута

Пример детализации для ситуации, требующей изменения маршрута:

```json
{
  "type": "route_proposal",
  "to": "write-prd",
  "reason": "Требование допускает два несовместимых сценария; нужно уточнить PRD"
}
```

`to` выбирается из известных операций Nav. Контроллер привязывает предложение
к текущей операции и сохраняет один ожидающий запрос основного поезда:
идентификатор, цель, причину и состояние решения. Reviewers возвращают findings
и рекомендации оркестратору. Обычные однозначные переходы остаются в коде;
оркестратор может запросить консультацию и перед таким переходом.

В обычном режиме запрос отображается в основном чате, например:
«В требованиях есть противоречие. Предлагаю вернуться к PRD. Продолжить?»
На карте сразу появляется предложенная дорога в туннель к PRD с красным
светофором. Поезд остаётся на месте, целевая операция ещё не запускается.

Два способа ответа разрешают один и тот же запрос:

- Зелёный на карте передаёт контроллеру явное подтверждение идентификатора запроса.
- Ответ в основном чате, например «да, редактируем PRD», интерпретирует
  оркестратор в контексте ожидающего запроса. Его структурированный результат
  различает согласие, отказ и продолжение обсуждения. Связь с фактическим новым
  сообщением пользователя задаёт контроллер. Реплики модели или Side-сессии
  не могут служить пользовательским разрешением.

После согласия код записывает источник решения, переключает светофор на зелёный
и продолжает маршрут без дополнительного подтверждения. Неоднозначный ответ
оставляет запрос открытым и поезд остановленным; модель продолжает обсуждение.
Отказ отменяет предложение. Повторный клик или ответ на уже заменённый запрос
не запускает второй переход. Состояние ожидания хранится в той же записи запуска,
поэтому перезагрузка страницы не превращает его в разрешение.

Понимание свободной фразы остаётся модельной оценкой; код проверяет происхождение
ответа и актуальность запроса, но не доказывает смысл согласия. Эту часть нужно
проверить на согласии, отрицании, условном ответе и уточняющем вопросе. Отдельный
агент для интерпретации ответа не требуется.

В `/autonomous` контроллер автоматически принимает предложение оркестратора
и фиксирует источник решения `autonomous`. Вопрос пользователю и ожидание
подтверждения не создаются; поезд следует выбранным маршрутом. Это тот же
механизм перехода с другой политикой разрешения. Ручной красный, Pause и Stop
остаются действующими ограничениями и автоматически не снимаются.

Модели доступна только подача feedback и предложения. Технически общий feedback
можно передавать через scoped-инструмент DSH с небольшой схемой; отдельные
инструменты всех возможных переходов не требуются. Разрешение и запуск принадлежат
контроллеру. `concludeTurn()` позволяет закончить ход после подачи запроса,
оставив сессию доступной для обсуждения; ждать пользователя внутри незавершённого
вызова модели не требуется. DSH поддерживает `outputSchema` для субагентов,
но основной сессии нужен собственный обработчик feedback.

Проверяются форма предложения, актуальная операция и доступность цели.
Без корректного предложения контроллер не угадывает маршрут по произвольной
прозе. Старые обязательные пакеты артефактов этими проверками не восстанавливаются.
Перед исполнением разрешённого перехода контроллер прекращает новые запуски
на прежнем участке и дожидается завершения либо отмены его активных исполнителей.
Поздний ответ старой попытки не переключает уже изменённый маршрут.

При возврате к PRD сохраняются сделанный код и история проверок. Модель получает
причину возврата и доступные материалы, уточняет требования и выбирает дальнейший
маршрут по содержанию изменений. Автоматический сброс всех последующих артефактов
и безусловный повтор всего workflow не требуются. Туннель отображает предложение
ещё до разрешения; движение по нему начинается после разрешения контроллера.

## Стек интерфейса

Выбран Svelte 5. Предлагаемая сборка — TypeScript и Vite с выпуском статических
HTML/CSS/JS для сервера DSH. Прямое использование React-компонентов DSH
в эту страницу не закладывается.

- SVG-компоненты отображают рельсы, станции, поезда, персонажей и вертолёт.
- `@panzoom/panzoom` остаётся кандидатом для перемещения и масштабирования;
  его пригодность подтвердит прототип согласованной карты.
- Реактивное состояние Svelte связывает интерфейс с событиями DSH.
- Средства анимации Svelte и браузера обеспечивают визуальные переходы.
  Движение поездов использует геометрию SVG-путей.
- Состояние процесса и геометрия карты отделены от оформления объектов:
  замена схематичного символа детализированным сохраняет его поведение.

Предлагаются три уровня детализации одной плавно масштабируемой карты:
весь маршрут без подписей, участок с названиями и статусами, отдельная операция
с настройками ролей. Пороги уточняются на прототипе по читаемости.
Панели и открытые элементы управления сохраняют нормальный экранный размер.

Этот стек рассчитан на весь обсуждённый функционал: параллельных исполнителей,
динамические настройки, туннельные возвраты, индикаторы контекста, потоковый
Side Chat и управление запуском. Интеграция с DSH и производительность
совместной работы карты, анимаций, чата и настроек пока не проверены прототипом.

## Контракты как настройки

Вместо длинной инструкции с неизменяемым порядком каждая операция получает:
цель, доступные входные материалы, выбранный состав ролей, эффективные настройки
и ожидаемый результат выполняемой работы.

| Прежнее правило | Предложение для Nav 27 |
| --- | --- |
| Verify обязателен по tier | Состав verify задан настройками; tier предлагает начальные значения |
| Фиксированный основной reviewer и co-reviewers | Независимо включаемые роли с выбираемыми моделями |
| Обязательный red-verify | Включаемая операция |
| Фиксированная модель Judge | Выбранная модель в штатной DSH-сессии |
| Обязательные консультации Judge | Начальная политика консультаций, которую можно менять |
| Фиксированный пакет протоколов | Результаты только реально выполняемых операций |
| Предыдущий отчёт обязателен для перехода | Краткий результат шага и доступные предметные материалы |
| Строгий doctor перед каждым gate | Проверки готовности по выбранной политике, без требований к отключённым шагам |

Старые runtime-инструкции нельзя просто подключить целиком: их обязательные
review, модели и handoffs будут противоречить UI. В Nav переносится полезное
содержание команд; механика и настройки исключаются из жёстких текстовых правил.
Не нужен отдельный переключатель для каждого предложения старого workflow.

Предлагаемая минимальная семантика результата операции:

- `completed`: операция выполнила свою работу; verdict хранится отдельно,
  поэтому завершённый reviewer может вернуть `FAIL`;
- `skipped`: операция отключена настройками;
- `failed`: исполнение завершилось ошибкой;
- `interrupted`: работу остановили или она оборвалась.

Эти значения относятся к операции, а не заменяют весь task lifecycle.
Пример краткой записи о закрытии задачи, а не новый обязательный файл:

```json
{
  "task": "TASK-...",
  "status": "done",
  "execution": "completed",
  "verify": { "status": "skipped", "reason": "all_reviewers_disabled" },
  "redVerify": { "status": "skipped", "reason": "disabled" },
  "configRevision": 12
}
```

Такое закрытие означает «реализация завершена, независимые проверки пропущены».
Оно не означает `PASS`. Дополнительные отчёты о несуществующих проверках не нужны.

Если основной verify-агент отключён, остальные включённые reviewers продолжают
работать и возвращают собственные результаты. Код собирает их; оркестратор
разбирает содержательные противоречия при необходимости. Новый обязательный
агент-сводчик вместо отключённого не создаётся.

Если включённый агент упал, это ошибка, а не skip. Изменение настроек не стирает
уже полученные FAIL или историю предыдущих попыток. Оператор может выбрать
обход следующей проверки; основание перехода будет новым решением, не фиктивным PASS.

Артефакты предметной области тоже используются по фактическому наличию.
Например, отключение design не создаёт пустую «успешную» архитектурную спецификацию:
исполнитель получает существующие требования, код и пояснения. Он запрашивает
недостающую информацию только если она действительно нужна для задачи.
Контроллер не требует весь прежний набор файлов по умолчанию.

## Изменение настроек во время работы

- При входе в операцию фиксируется состав её включённых ролей. Изменение состава
  после старта действует на следующий запуск операции.
- Модель, провайдер и reasoning фиксируются при запуске конкретного исполнителя.
  Ещё не запущенный исполнитель получает последние сохранённые настройки.
- Уже работающий исполнитель заканчивает со своим снимком конфигурации.
  Отключение не является скрытым прерыванием; для прерывания есть Stop.
- UI различает применённые и ожидающие настройки. Для изменений достаточно
  номера ревизии и короткой истории; сохранение проверяет ожидаемую ревизию.
- Оркестратор меняет модель на остановке без активного запроса к его модели.
  Визуальная остановка поезда сама по себе не доказывает готовность к смене.
- Judge меняет модель между консультациями. Пока вертолёт занят, новая настройка
  ожидает следующего вылета; смена человечка показывается при применении выбора.
- Модель и reasoning выбираются из возможностей конкретного DSH-подключения.

Начальные пресеты могут повторять полезные привычки DevRails 26, но не сохраняют
жёсткую привязку к Codex-моделям или обязательным проверкам.

## Субагенты и lifecycle DSH

Контроллер запускает штатный `ctx.subagents.startActivation` с backend `spawn`,
живым оркестратором как parent и `agentOptions` выбранной роли. `spawn` здесь
означает механизм DSH; модельный провайдер передаётся отдельно в `agentOptions`.
Результаты возвращаются контроллеру через `delivery: 'caller'`, затем нужное
резюме добавляется оркестратору. Стандартные проверки не требуют от LLM ручного spawn.

Для содержательной дополнительной делегации модель сообщает нужную роль и цель;
исполнение и выбор конфигурации остаются у контроллера DSH. Прямые альтернативные
пути запуска из старых skills не переносятся.

Главный процесс Nav не требуется упаковывать в один `workflowEngine` script.
Небольшой контроллер может вызывать штатных субагентов непосредственно.
Если используется `ctx.workflowEngine.start`, создавший run код вызывает
`await run.dispose()` в `finally` при любом результате. Аналогично освобождаются
принадлежащие контроллеру activation handles. Результат работы и освобождение
её ресурсов — разные обязательства владельца.

## Восстановление и управление

Отсутствие resume у DSH workflow-script не отменяет восстановление DevRails
через Memory Bank. Предлагается сохранять там одну компактную запись текущего
запуска: операция, задача, применённые настройки и их изменения, ссылки на
DSH-сессии, краткие результаты выполненных и пропущенных шагов, следующее действие,
светофоры и привязки Side-чатов к карте.
Точное расположение этой записи определится при реализации; новый набор
раздельных отчётов не нужен.

Это упрощает прежнее предложение: состояние маршрута не требуется параллельно
вести в DSH storage и экспортировать в status.md. DSH хранит свои сессии;
Memory Bank хранит состояние проекта и достаточный контекст продолжения.

После рестарта контроллер читает запись, доступные результаты и файлы проекта.
Сохранённый результат повторно не исполняется. Оборванный шаг передаётся модели
как продолжение с осмотром уже сделанного, а не как слепой повтор всех действий.
Недоступную сессию можно заменить новой с контекстом Memory Bank.
Точное продолжение прерванного модельного запроса не обещается.

- Play начинает или продолжает выбранный маршрут.
- Pause прекращает допуск новых операций и даёт текущей работе дойти до границы;
  UI показывает ожидание остановки.
- Stop прерывает активные операции через DSH и ожидает завершения их ресурсов.
  Уже сделанные изменения в проекте сохраняются.

Предлагаемая семантика красного светофора:

- Ожидание разрешения на предложенный маршрут отображается красным автоматически.
  Зелёный пользователя или его согласие в основном чате разрешают этот запрос.
  Для консультации без смены маршрута действует тот же механизм на основном пути.
  Этот красный отличается по причине от отдельно установленного ручного запрета:
  `/autonomous` снимает необходимость спрашивать, но не ручной запрет движения.
- На будущем переходе красный запрещает вход. Когда очередь доходит до него,
  контроллер сохраняет ожидающий маршрут и сообщает оркестратору об остановке.
  Не требуется держать модельный запрос открытым или опрашивать модель в цикле.
- Если красный включён на уже выполняемом перегоне, контроллер прекращает новые
  действия и запрашивает отмену текущей работы через DSH. До фактического окончания
  UI показывает «останавливается», затем ожидание инструкции. Это прерывание,
  а не заморозка запроса; уже выполненные изменения сохраняются.
- Смена сигнала и допуск следующей операции обрабатываются одним контроллером
  последовательно. Play и собственный ответ модели не обходят ручной красный.
  Сигнал сохраняется при перезагрузке страницы и восстановлении процесса.
- В основном чате можно выяснить причину, уточнить требования и заменить
  ожидающий маршрут. Пока действует остановка, guards инструментов не допускают
  самостоятельное продолжение работы или изменение проекта; обсуждение и чтение
  доступны. Одной инструкции в prompt для такой остановки недостаточно.
- Зелёный снимает соответствующую блокировку светофора. Явная команда пользователя
  продолжить в основном чате может сделать то же; обычное обсуждение её не снимает.
  Если других остановок нет, маршрут продолжается; отдельно включённые Pause/Stop
  требуют Play. После прерывания продолжается работа по фактическому состоянию,
  не прежний сетевой запрос.

## Side Chat

В DSH есть обычный `session.fork`: без `atSeq` он берёт последнюю завершённую
часть истории; явная граница позволяет сделать срез и внутри текущего turn.
DSH завершает открытый хвост синтетическими fork-событиями только в копии,
не изменяя исходную сессию. `buildForkSeed` доступен отдельно для создания
сессии со своей композицией через штатный `ctx.agents.create`.

Предложение: Side Chat создаётся обычной независимой DSH-сессией на основе
текущего доступного среза оркестратора, с настройкой Side-роли до первого запроса.
Чат получает свежий снимок Nav-состояния при каждом вопросе. Это важно:
форк — снимок, не автоматическая подписка на будущий диалог родителя.

Side-роли доступны ответы и чтение состояния, но не команды управления поездом
или изменения проекта. Используется scoped tool composition/guard DSH;
одной фразы «read-only» в prompt недостаточно. Встроенный fork сам по себе
такую роль не задаёт. Контекст копируется, инструменты выполнения не запускаются
заново. Навигация и остановка родительского процесса для открытия чата не нужны.

Клик по корпусу паровозика создаёт Side-сессию и её свёрнутое окно чуть ниже
текущей позиции. Координаты относятся к карте, а не экрану: поезд движется дальше,
окно остаётся на месте, перемещаясь на экране вместе с pan/zoom. Таких окон может
быть несколько; окончание операции и повторный проход по участку их не удаляют.
Привязки `sessionId` и позиции сохраняются с запуском; переписку хранит DSH.

В свёрнутом окне — только заполненность контекста собственной Side-сессии
в процентах; при отсутствии измерения — `—`. Клик разворачивает полноценный
HTML-чат нормального экранного размера. Сворачивание возвращает маркер на карту.
При максимальном отдалении остаётся объект без текста, как у остальных объектов
карты; процент появляется на масштабе, где он читаем.

DEL внутри чата удаляет его с карты. Для lifecycle предлагается штатная архивация
DSH-сессии с остановкой её активности; это сохраняет историю в архиве DSH,
а не обещает физическое удаление журнала. Привязка убирается после успешной
архивации. Остальные чаты и основной процесс продолжаются независимо.

## Основной чат в DSH

Клик по машинисту открывает именно сессию оркестратора в штатном DSH UI;
эта область клика не создаёт Side Chat. Открытие чата само по себе не останавливает
workflow и не создаёт копию основной сессии.

В проверенном DSH есть `ctx.uiWorkspace.openSession(sessionId)`, но готового
общего URL-перехода к произвольной сессии не найдено. Предлагается небольшой
клиентский компонент Nav в стандартной оболочке DSH: он принимает идентификатор
из ссылки Nav и вызывает штатный метод, когда сессия доступна. Формат ссылки
будет принадлежать плагину; это ещё не существующий deep link DSH.
Svelte-странице карты не требуется загружать React-интерфейс DSH.

## Визуальный контракт

- Основной маршрут направлен слева направо. Максимальное отдаление помещает
  всю карту в viewport; подписи объектов и настройки скрываются, остаются
  объекты, цвета и общая структура. При приближении появляются тактические детали.
  Play/Pause/Stop остаются читаемыми вне масштабируемой сцены.
- Главный паровоз представляет оркестратора и движение процесса. Выбор
  машиниста доступен на остановке. Цвета: голубой, оранжевый, фиолетовый,
  белый и чёрный. Цвет отличает выбранного персонажа, модель подписана отдельно.
- База Judge находится рядом с маршрутом; вертолёт паркуется на площадке H.
  На базе три человечка с именами моделей и выпадающими списками. Это три
  настраиваемых слота выбора, а не три постоянно запущенных Judge.
  При смене выбора старый пилот идёт на базу, новый — к вертолёту.
- Локальная петля реализации и проверок возвращается к тому же месту входа
  в реализацию задачи. Независимые reviewers представлены параллельными
  паровозиками. При принятии результата поезд выходит на основной маршрут;
  при необходимости исправления повторяет цикл.
- Для возврата на более раннюю команду появляется короткая разворотная ветка
  к туннелю. Выезд расположен перед целевой станцией и примыкает дугой к пути.
  В обычном режиме ветка появляется при предложении маршрута, с красным сигналом.
  После разрешения камера отдаляется, поезд входит, примерно через секунду
  выходит; камера приближается к месту выхода. В `/autonomous` подтверждение
  автоматическое. Движение отражает уже разрешённое изменение маршрута.
- Груз поезда и вертолёта отображает заполнение контекста соответствующей
  сессии. Это не сумма контекстов всех агентов и не процент готовности задачи.
- DSH предоставляет `contextPressure` с `projectedTokens`, `pressureTokens`
  и `contextWindow`. Отношение — приближённая оценка; если данных нет,
  UI показывает неизвестное значение. Изменение модели может временно
  оставить измерение от предыдущего запроса.
- Счётчик compaction выводится при значении больше нуля. Он считает успешно
  завершённые компактизации по `compactionId` в отображаемой сессии;
  неудачные попытки и обычный prune не увеличивают этот счётчик.
- Под картой — состояние агентов. Side-чаты закреплены в точках своего создания
  и разворачиваются по клику. Машинист открывает основной чат DSH.
  Пропущенные станции/проверки визуально отличаются от успешно выполненных.

Референс показывает композицию и метафору. Он не заменяет полный граф команд,
не утверждает конкретные модели и не задаёт окончательные пороги zoom.

[Первый визуальный референс](docs/nav27/railway-reference-01.png) создан встроенным
imagegen; [исходный prompt](docs/nav27/railway-reference-01.prompt.txt).
Это вариант визуального направления, не утверждённая схема соединений.
В следующем эскизе возврат reviewers нужно перенести непосредственно ко входу
в реализацию задачи: на первом изображении он находится раньше, перед фичами.
Для первой версии выбрана схематичная SVG-карта. Этот референс остаётся
ориентиром последующего оформления; точная схема путей ещё согласуется.
