# Как работает DevRails 26

DevRails сохраняет проектный контекст и помогает пройти путь от замысла до
проверенного результата. Memory Bank — основа работы: требования, технические
решения, фичи, задачи и результаты доступны следующей сессии.

## Основной flow

```text
Замысел и требования → фичи и дизайн → задачи → реализация и проверка → память
```

Этапы обозначают нужные результаты, а не обязательные команды. Агент может
совместить несколько этапов в одной просьбе, использовать уже принятые решения
и обновить затронутые документы вместе с кодом. Если для текущей задачи не
хватает существенной информации, её нужно прояснить; отсутствие отдельного
документа или approval не означает автоматически, что информации нет.

Общая runtime-политика находится в
`.memory-bank/workflows/execute-loop.md#working-policy`.

В обычной ручной работе агент консультируется с оператором по новым
содержательным продуктовым, техническим и процессным решениям. Самостоятельный
выбор разрешён на автопилоте или по явному поручению действовать автономно,
в пределах согласованной цели и ограничений. Молчание не даёт автономности.
Принятое решение исполняется без повторного согласования.

Отдельные ревью, свежие контексты, TDD, doctor и подробные протоколы
рекомендательны. Оператор может пропустить шаг обычной фразой, без оформления
исключения. Агент сохраняет правдивую память: пропущенный тест не становится
PASS, неразрешённая зависимость — выполненной, а новая версия кода — проверенной
только потому, что когда-то проверялась предыдущая.

## Memory Bank и рабочие записи

| Место | Назначение |
|---|---|
| `.memory-bank/constitution.md` | Принципы проекта, границы автономности и явные ограничения |
| `.memory-bank/analysis/brief.md`, `prd.md` | Замысел и согласованные требования продукта |
| `.memory-bank/product.md`, `requirements.md` | Продуктовая структура, REQ и traceability |
| `.memory-bank/epics/`, `features/` | Декомпозиция и acceptance criteria |
| `.memory-bank/architecture/`, `contracts/`, `domains/`, `states/` | Канонические технические решения, границы и модели |
| `.memory-bank/guides/`, `testing/`, `runbooks/`, `adrs/` | Практическое применение, проверки, эксплуатация и решения |
| `.memory-bank/spec-index.md` | Ссылки на спецификации по предмету |
| `.memory-bank/spec-backbone.md` | Общий дизайн и состояние его проработки |
| `.memory-bank/contracts/boundary-map.md` | Принятые модули и связи Consumer → Provider |
| `.memory-bank/tasks/` | JSON-карточки и единственный индекс задач |
| `.protocols/<TASK_ID>/` | Дополнительные записи для выполнения/продолжения, когда полезны |
| `.tasks/<TASK_ID>/` | Подробные evidence, логи и отчёты, когда нужны |
| `.protocols/AUTONOMOUS-RUN/status.md` | Краткая точка продолжения автономного запуска |
| `PAPERCUTS/` | Подтверждённые мелкие проблемы; `TECHDEBTS/` — отчёты `/tech-debt` |

Подробная память сохраняется. Ссылки предпочтительнее многократного копирования
одних сведений в карточку, план и отчёт. Для небольшой задачи может хватить
карточки, проверок и обновления затронутой спецификации. Полный протокол
оправдан, если помогает сложной работе или её возобновлению.

У требований, спецификаций и задач разные функции: REQ объясняет зачем,
feature AC описывает наблюдаемый результат, спецификация — принятую техническую
форму, задача — ограниченный результат реализации. Subject-based specs не
нужно дублировать в отдельном документе на каждую фичу. Feature связывает
применимые спецификации.

Planning Revision и маркеры reconciliation помогают найти изменённые
предпосылки. Они не требуют повторно ревьюить незатронутую работу и не являются
формальным допуском к исполнению. При изменении решения агент согласованно
обновляет затронутые документы, сохраняя историю фактических результатов.

## Подготовка проекта

Для Greenfield сначала проясняются замысел и нужные ограничения, затем
формируются фичи, технические решения и задачи. `/grill-me`, `/write-prd`,
`/prd-to-features`, `/spec-design` и `/feature-to-tasks` помогают этой работе.
Достаточно той глубины, которая позволяет понять и реализовать результат.

Foundation — минимальный исполнимый baseline: например, сборка, запуск и
базовое взаимодействие компонентов. Если он нужен, `/foundation-to-tasks`
использует обычные карточки с `FT-000` и `REQ-000`. `W0` зарезервирован для
Foundation; продуктовые задачи используют `W1+`. Реальные зависимости
отражаются в `depends_on`. Не нужно создавать Foundation только ради этапа
или завершать независимую подготовительную работу до планирования продукта.

В Brownfield агент сначала восстанавливает фактическое состояние нужной части
проекта. `/map-codebase` помогает сохранить evidence-backed baseline, но код
не становится автоматически источником желаемых требований. Затем применяется
согласованная delta. Существующий baseline можно использовать повторно.

## Карточки задач

Формат и существующие поля в этой переработке сохранены. Они обслуживают
контекст, зависимости, доказательства и продолжение работы, а не только отчёты.

```text
.memory-bank/tasks/index.json
.memory-bank/tasks/TASK-NNN-TN-FT-NNN-WN.task.json
.memory-bank/schemas/task.schema.json
```

ID, имя файла и поля `tier`, `feature`, `wave` согласуются. JSON-индекс содержит
пары `id`/`file`. Старый Markdown backlog не является альтернативным реестром.

| Поля | Что сохраняют |
|---|---|
| `id`, `title`, `status` | Идентичность, назначение и текущее состояние |
| `feature`, `reqs` | Связь результата с продуктом |
| `depends_on`, `wave` | Реальные предпосылки и группировка работы |
| `tier` | Оценка риска для выбора глубины работы |
| `purpose`, `success_outcome`, `anti_goals` | Зачем задача, ожидаемый результат и исключённая работа |
| `source_artifacts`, `normative_inputs` | Источники, exact AC links и применимые спецификации |
| `constraints`, `invariants` | Существенные ограничения и сохраняемые свойства |
| `touched_files` | Ожидаемая, неисчерпывающая область изменений |
| `runtime_context` | Явно заданные write boundary, forbidden scope и stop conditions |
| `gates`, `verification_targets`, `evidence_required` | Команды, способ проверки и ожидаемые доказательства |
| `verify` | Фактический результат и выполненные, пропущенные или недоступные проверки |
| `docs` | Существующее поле ссылок; schema-совместимость сохранена |

Schema по-прежнему содержит 18 обязательных полей и 4 необязательных.
Обязательное array-поле может быть пустым, когда применимого содержания нет.
Это не повод придумывать ограничения или проверки ради заполнения формы.
Значимые для выполнения сведения остаются в карточке или по прямым ссылкам.

`touched_files` не запрещает добавить другой нужный файл в рамках того же
результата. Непустой `runtime_context.write_boundary` — намеренно заданная
граница, её нельзя игнорировать. Это literal project-relative POSIX paths,
а не globs; deprecated `allowed_write_scope` остаётся только read alias.

Префикс заголовка `Production acceptance:` имеет служебный смысл: такие задачи
ждут явного запуска после deployment и не входят в development queue. Его
нельзя переводить или удалять как чисто косметическую часть названия.

Состояния:

```text
planned | ready | in_progress | blocked | done | done_for_prod | failed
```

`ready` означает, что реальные предпосылки выполнены. `done_for_prod` означает
завершённую разработку с остающейся production acceptance, а не успешную
проверку production. Повторный запуск сверяется с карточкой и evidence, чтобы
не воспроизвести уже выполненное небезопасное действие.

## Исполнение и проверка

`/exe` помогает выполнить выбранную задачу и сохранить результат. В рамках
согласованной работы тот же агент может поправить затронутый план и спеки,
выполнить проверки и закрыть задачу. Отдельный closure-owner документ не нужен.
При запуске внутри scheduler итоговый task state записывает scheduler.

`T0` — безопасная документация; `T1` — локальное изменение; `T2` — API,
данные, состояние или несколько модулей; `T3` — безопасность, production,
платежи или необратимые последствия. Tier помогает оценить риск, но не задаёт
обязательное число документов, агентов или проходов проверки.

Подходящая проверка доказывает нужный результат с учётом реального риска.
TDD и RED/GREEN полезны, когда подходят работе; отсутствие предварительного
RED не требует искусственно создавать или восстанавливать его задним числом.
`verification_targets` и `evidence_required` описывают план проверки,
а `verify` — наблюдённый результат. Это разные виды сведений.

Отдельный `/verify` проверяет функциональный результат; `/red-verify`
помогает искать содержательные ошибки и ложный успех; `/add-tests` добавляет
нужные тесты; `/debug` исследует конкретный сбой. Ни один отдельный вызов не
обязателен только из-за tier. Явно запрошенное независимое/read-only review
сохраняет свою границу и не превращается в незапрошенную реализацию.

## Автономная работа

`/autopilot` выполняет существующую продуктовую очередь; `/autonomous`
проходит полный flow и при необходимости выполняет Foundation, затем
использует `/autopilot` для продукта. Эти команды предоставляют автономность
внутри поручения. Выход за его границы требует решения оператора.

По умолчанию задачи выполняются последовательно. Сохраняются текущее действие,
результат и следующая точка продолжения. Неудача не становится успехом:
реальная причина фиксируется, зависимая работа ждёт её устранения. Ограниченные
повторы помогают исправлению, но не создают бесконечный цикл. `/debug` доступен
при неясной причине сбоя.

Fresh contexts и delegated agents используются по пользе. Экспериментальная
параллельность остаётся явным `--experimental-parallel` с изоляцией и
непересекающимися hard write boundaries; `touched_files` не доказывает
независимость записей.

`/multipilot` и `/multiagentic` добавляют read-only Judge к соответствующему
базовому режиму без второй очереди и другого lifecycle.

## Диагностика и обслуживание

`/mb-sync` помогает согласовать уже выполненные изменения с проектной памятью.
Обновление можно сделать в текущей работе; отдельный вызов или wave ceremony
не обязательны. `/mb-garden` обслуживает ссылки, индексы и drift. Семантические
решения подчиняются той же границе автономности.

`mb-lint` проверяет структуру, допустимые поля, ID, ссылки и cycles.
`mb-doctor` добавляет диагностику состояния и неполного контекста:

```bash
node .memory-bank/scripts/mb-lint.mjs
node .memory-bank/scripts/mb-doctor.mjs
node .memory-bank/scripts/mb-doctor.mjs --strict --json
```

Это инструменты по необходимости. `--strict` запрашивает углублённую
диагностику, а не допуск к автопилоту. Ошибки повреждённых данных и реальных
зависимостей сохраняют значение; советы о полноте планирования не требуют
создавать документы лишь ради зелёного отчёта. Compact protocol или evidence
в карточке допустимы на любом tier. Отсутствие отдельного semantic-pass,
полного протокола или closure-owner записи не означает дефект результата.

## Установка и обновление

Из checkout DevRails:

```bash
node scripts/install-framework.mjs
```

Установщик предлагает target и политику существующего `AGENTS.md`, готовит
временную копию и устанавливает полный набор runtime skills для Codex и
Claude. Чужие skills с совпадающими именами не перезаписываются автоматически:
конфликты перечисляются до записи.

Non-interactive установка и обновление:

```bash
node scripts/install-framework.mjs --bootstrap --target /path/to/project --yes
node scripts/install-framework.mjs --bootstrap --sync --target /path/to/project --yes
```

Только runtime skills, без Memory Bank:

```bash
node scripts/install-framework.mjs --install-only --target /path/to/project --yes
```

Только skeleton/managed Memory Bank assets:

```bash
node scripts/install-framework.mjs --bootstrap-only --target /path/to/project --yes
```

`--bootstrap-only --sync` не обновляет runtime skills. Для согласованного
framework upgrade используется `--bootstrap --sync`. `/start` и `/mb-init`
маршрутизируют к внешнему installer из известного checkout, а не копируют
bootstrap logic в проект. После установки продолжается исходный запрос.

Fresh bootstrap создаёт пустой `tasks/index.json`, schema, структуру Memory
Bank и framework references. Он не выдумывает продуктовые задачи, Foundation
или принятые требования.

Sync обновляет framework-owned schema, workflows, roles, protocol templates,
scripts и сгенерированные runtime skills. Существующие project/mixed документы,
карточки, заполненные протоколы и `boundary-map.md` сохраняются. В skills index
обновляется только generator-managed блок установленного набора. Installer
sync и runtime `/mb-sync` выполняют разные задачи.

## Source-only модель

Canonical source общего поведения находится в `skills/_shared/`. Три package
entrypoints — `start`, `mb-init`, `mb-garden` — обеспечивают упаковку и bootstrap.
Runtime команды генерируются из `skills/_shared/references/commands/*.md`.

```text
canonical source → временная копия → vendor-shared → runtime skills → bootstrap/sync
```

В target команды находятся в `.agents/skills/` и `.claude/skills/`;
`.codex/` предназначен для конфигурации. Прямой `npx skills add <repo>` для
source-only DevRails не поддерживается. Generated package-local `shared-*`
не редактируются и не коммитятся. Локальный Memory Bank source-репозитория —
ignored dogfood output, а не исходники framework.

Проверки изменений framework:

```bash
npm run check:syntax --silent
npm run test:mb-doctor --silent
npm run test:install-sync --silent
find skills -path 'skills/_shared' -prune -o -type f -name 'shared-*' -print | wc -l
```

Последняя команда должна вернуть `0`. Установку проверяют в изолированном
временном target, а не развёртыванием generated-копий в source tree.
