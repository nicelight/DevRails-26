# Project Map — DevRails Nav 27

## Read First

Before changing this repository, read `AGENTS.md`, `README.md`, `package.json`,
`scripts/install-framework.mjs` and `scripts/vendor-shared.mjs`.
For semantic scope and acceptance, use `docs/nav27/SEMANTIC_INVENTORY.md`,
`TRANSITIONS.md` and `SEMANTIC_ACCEPTANCE.md`.

This branch contains adapted workflow semantics and deterministic validators.
All models/subagents are specified to use DSH; host code owns scheduling,
launches, lifecycle, budgets and recovery sequencing. **The DSH plugin/controller
and UI are not implemented.** Current `.agents/.claude` generation is legacy
packaging used to validate delivery, not a DSH adapter.

## Source-Only Packaging

```text

  -> temporary repository copy
  -> scripts/vendor-shared.mjs
```

Never edit or commit generated package-local `shared-*` files. Direct
`npx skills add` is unsupported. Local `.memory-bank/`, `.agents/`, `.claude/`,
`.codex/`, `.protocols/` and `.tasks/` are ignored generated dogfood output,
not canonical source or agent scratch space. Use isolated temporary targets.

`package.json` names DevRails Nav 27. Existing bin names, repository-origin URLs,
paths, environment flags and generated ownership markers remain compatibility
identities. A `Generated by DevRails 26` marker is used for safe managed-file
recognition; it is not the current product display name.

## Common Workflow Contract

`workflows/autonomy-policy.md` owns DSH-only runtime, one required compact
structured flow feedback, ordinary/autonomous decisions, conditional checks,
negative-result disposition and evidence-aware recovery. Exact feedback fields
and transport are deferred. Every nonstandard branch/repair and main-path
consultation uses the same decision flow; autonomous policy persists across
`autonomous` → `autopilot`, preserving manual stops and real permissions.

`execute-loop.md` owns subject boundaries and immediate handoffs; it is not a
prompt scheduler. `multiagents_with_judge.md` adds conditional read-only route
assessment, not an immutable Judge or second lifecycle. No fixed model/fanout.

All verify off means skipped/no report, and implemented work may close without
PASS. Main-off does not create a replacement main; candidate-only code review
is not functional proof. Red-verify is independently selectable, including
red-alone with absent functional proof explicitly stated. Local exe checks
are independently configurable and enabled by default. These working defaults
are adjustable. Actual negatives remain evidence with scoped disposition.

## Task Registry And Evidence Hotspots

Task registry remains `.memory-bank/tasks/index.json` plus indexed JSON records.
IDs `TASK-NNN-TN-FT-NNN-WN` agree with tier, feature and wave; product uses W1+,
FT-000 is reserved Foundation. Existing status vocabulary is unchanged; the host
owns all lifecycle writes. Models author subject planning/work and return facts.

`workflows/tier-policy.md` owns task claims, dependencies, hard boundaries,
selected proof and closure authority. `touched_files` is advisory;
`runtime_context.write_boundary` has literal POSIX segment-prefix semantics.
`allowed_write_scope` is a deprecated read alias. Do not add another task schema,
registry, lifecycle or durable context object.

New Nav applicability/results use existing `task.verify`, `stage: workflow`,
with stable attempt and `selected`: design/local_checks/task red/feature
red booleans, verify participants and protocol filenames. `protocols: []` is
valid. Settings change only at initial/stopped-ready stations after the accepted
result of all selected participants. Green freezes the whole leg, including
unstarted participants. Local checks belong to exe; verify/red are later legs
and can change at a permitted stop without a new attempt or repeated exe.
Manual red/Pause stops next admission after the current leg; passing a station
without a stop does not enable editing. Diagnostics use retained choices,
never live configuration to reinterpret evidence. Results remain immutable;
new attempts preserve history and inline evidence can satisfy selected work.
Code candidates and functional verdicts remain distinct. Negative repair needs
later applicable selected success, or an explicit scoped continuation decision.

Legacy entries without the Nav marker keep historical evidence checks; sync
must not fabricate a marker or historical proof. Preserve partial effects,
completed results, task identity and production remainder through recovery.

Touch points: `feature-to-tasks`, `foundation-to-tasks`, `exe`, `verify`,
`red-verify`, `mb-sync`, `autopilot`, `autonomous`, tier policy, protocol templates,
`init-mb.js`, structure reference, lint, doctor task-readiness/terminal-compat/
acceptance-trace modules and their regression scripts.

## Product, SDD And Foundation Hotspots

Product targets/acceptance belong to `write-prd`; REQ/EP/FT and stable ACs to
`prd-to-features`; one-feature task cards to `feature-to-tasks`. Mapping records
as-is evidence, never accepted target authority. Material acceptance retains
REQ/AC/task ownership and selected proof; done alone does not establish verified.

`sdd-design-contract.md` governs source authority, canonical subject ownership,
SDD coverage and validation. `spec-design` owns initial design;
`spec-redesign` owns accepted changes and evidence-bounded none/bounded/global
impact. Optional matrix/ADR/duo artifacts cannot become unconditional gates.
Disabled design needs no placeholder backbone or positive revision.

When revision exists, global impact increments it once; bounded impact preserves
it and marks only affected feature planning. Without revision, actual affected
planning uses the existing reconciliation marker. Enabled reviews bind to their
actual accepted basis; disabled reviews need no APPROVE.

Detailed module identity/Consumer → Provider topology belongs to
`contracts/boundary-map.md`; architecture shape and stable AD rules belong to
`architecture/system-architecture.md`. Subject specs live under architecture,
contracts, domains, states, testing, runbooks, guides or adrs. Features link them,
not default FT-* design hubs. Optional behavior JSON examples have no new gate.

Foundation uses the ordinary FT-000 queue. Separate integrated proof gate is
conditional; `Gate Task: not_required` can accompany real required baseline
implementation. Existing accepted gate identity and real baseline dependencies
remain. Fresh bootstrap creates no Foundation tasks or accepted baseline.
Doctor's foundation-backbone module owns mechanical checks; semantic sufficiency
belongs to the selected subject owner.

## Validation Commands

```bash
npm run check:syntax --silent
npm run test:mb-doctor --silent
npm run test:install-sync --silent
find skills -path 'skills/_shared' -prune -o -type f -name 'shared-*' -print | wc -l
```

Source-only count must be `0`. For isolated delivery:

```bash
nav_target="$(mktemp -d)"
node scripts/install-framework.mjs --install-only --target "$nav_target/install-only" --yes
node scripts/install-framework.mjs --bootstrap --target "$nav_target/bootstrap" --yes
node scripts/install-framework.mjs --bootstrap --sync --target "$nav_target/bootstrap" --yes
(cd "$nav_target/bootstrap" && node .memory-bank/scripts/mb-doctor.mjs --json)
```

`MEMOBANK_KEEP_INSTALL_TMP=1` preserves the prepared copy when inspection of
package-local vendoring is necessary. Bootstrap-only sync does not update skills.
Full sync preserves project-owned files/evidence and refuses unknown collisions.
